# Backend

Node.js + TypeScript + Fastify, параметризованные SQL-запросы через `pg` напрямую (без ORM — единственный источник правды по схеме — `db/migrations/`). Подключается к Postgres ролью `groshik_app` (см. [`db/README.md`](../db/README.md)) — без прав на DDL.

## Запуск

```bash
# из корня репозитория: поднять БД + применить миграции + засеять контент
cp .env.example .env   # если ещё не сделано
docker compose up -d
set -a && source .env && set +a
./db/scripts/migrate.sh
psql "$DATABASE_URL" -f db/seed.sql   # тестовые квесты/товары/события

cd backend
npm install
npm run dev   # http://127.0.0.1:3000, читает ../.env
```

`GET /health` — проверка живости.

Локальный `APP_DATABASE_URL` использует `sslmode=disable`, потому что Docker PostgreSQL привязан к loopback и не поднимает TLS. Удалённый адрес принимается только с `sslmode=verify-full`; `sslmode=prefer` запрещён как неоднозначный для `pg` и `libpq`.

## Аутентификация

Без ПДн: нет email/пароля. Родитель регистрируется анонимно (`POST /auth/parent/register`) и получает непрозрачный bearer-токен. Ребёнок привязывается кодом приглашения (`POST /auth/parent/invites` → `POST /auth/child/register`). Токен передаётся как `Authorization: Bearer <token>` в каждом запросе; на сервере хранится только его SHA-256 хэш (`auth_credentials.token_hash`), не сам токен.

## Безопасность

- **Инъекции**: каждый запрос идёт через `query()`/`withTransaction()` из `src/lib/db.ts` с `$1, $2, ...` — ни один SQL не собирается конкатенацией строк. Плюс роль `groshik_app` физически не может выполнять DDL — второй рубеж, даже если где-то проскочит ошибка.
- **MITM**: см. `db/README.md` — на проде `APP_DATABASE_URL` обязан использовать `sslmode=verify-full`.
- **Заголовки/rate-limit**: `@fastify/helmet` + `@fastify/rate-limit` (120 запросов/мин на IP) подключены глобально.
- **Экономика**: любая операция с деньгами идёт через `postTransaction`/`transferBetweenWallets` в `src/lib/ledger.ts` — баланс всегда пересчитывается на сервере через `SELECT ... FOR UPDATE`, клиент никогда не может передать свой баланс.
- **Реванш/список ответов квеста**: `correctOptionCode` вырезается из `ui_spec` перед отправкой клиенту — правильный ответ никогда не уходит на устройство заранее.

## Интеграционный тест экономики

Интеграционная проверка экономики: после применения миграций и `db/seed.sql`
к **отдельной тестовой БД**, запустить из `backend`:
`ECONOMY_TEST_DATABASE_URL="postgres://groshik_app:...@127.0.0.1:55433/groshik?sslmode=disable" node --import tsx --test test/economy-integration.test.ts`.
Тест создаёт тестовые профили и журнал операций; его нельзя направлять на рабочую
БД. Без этой переменной обычный `npm test` пропускает интеграционный сценарий.

## Известные упрощения (не сделано)


- **ML-адаптивная сложность** — сейчас `child_profiles.difficulty` статическое поле (SIMPLE/ADVANCED), задаётся вручную при регистрации. Подключить модель — вопрос замены источника этого поля, эндпоинты не изменятся.
- **Случайные события/вредные советы триггерятся по запросу клиента** (`POST /pet-events/roll`, `POST /scam-offers/roll`), а не по расписанию — нет фоновой job-очереди. Экран экономики вызывает событие один раз при открытии нового игрового дня.
- **Сундук Морозко даёт денежный бонус (+10%)**, а не редкий предмет, как в идеальном сценарии ТЗ ("более ценные эпические предметы") — можно добавить случайный дроп предмета при сборе, схема это не блокирует.
- Для критичных контрактов БД, питомца и онбординга есть тесты (`npm test`), но backend пока не добавлен в отдельный CI job.
- Не задеплоено никуда — только локальный запуск. Для работы APK вне локальной сети бэкенд+БД должны быть захостены публично по HTTPS.
