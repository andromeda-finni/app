# База данных

PostgreSQL. Схема — plain SQL миграции в [`db/migrations/`](migrations/), применяются по порядку номеров и накатятся на любой Postgres 14+ (локальный Docker, self-hosted или managed — Supabase, RDS и т.д. — это обычный Postgres, миграции доедут и туда через `psql`/CLI провайдера).

Итоговая схема — упрощённая версия `groshik-er.dbml` (было 46 таблиц с полным compliance/consent/audit слоем и версионированием контента под живые релизы; здесь 23 таблицы — вся игровая механика без инфраструктуры под сбор и обработку персональных данных, которых продукт не собирает).

## Локальный запуск

```bash
cp .env.example .env      # подставить свои пароли
docker compose up -d      # поднимет Postgres 16 на 127.0.0.1:5432
set -a && source .env && set +a
./db/scripts/migrate.sh   # применит все миграции + заведёт роль groshik_app
```

Повторный запуск `migrate.sh` безопасен — уже применённые файлы пропускаются (таблица `schema_migrations`).

## Модель данных (23 таблицы)

- **Аккаунты**: `users`, `parent_profiles`, `child_profiles`, `parent_child_links` — без имени/возраста/email/телефона; `child_profiles` хранит только номер текущего шага и факт завершения онбординга.
- **Питомец**: `pets` (один вид на всех, кастомизация через `cosmetic_options` — цвет шерсти/аксессуар).
- **Обучающий контент**: `education_topics`, `quest_definitions`, `quest_steps`, `shop_items`.
- **Экономика**: `wallets` (SPENDABLE/SAVINGS/FROZEN), `transactions` (единый append-only леджер), `purchases`, `frost_chests` (Сундук Морозко: 3 дня → +10%).
- **Бюджетный цикл**: `game_periods`, `budget_plans`, `period_results`.
- **Задания**: `assignments` (системные квесты + родительские поручения в одной таблице), `quest_step_progress`.
- **Цели/инвентарь**: `financial_goals`, `inventory_items` (+ слот экипировки прямо на `pets`).
- **Случайные события питомца**: `pet_event_definitions`, `pet_event_occurrences` — решаются оплатой монетами (сперва SPENDABLE, при нехватке — SAVINGS).

## Безопасность

**SQL-инъекции.** Схема не защищает от инъекций сама по себе — это ответственность backend-кода. Правило: бэкенд **всегда** использует параметризованные запросы (`$1, $2, ...` через `pg`/любой ORM с bind-параметрами), никогда не собирает SQL конкатенацией строк с пользовательским вводом. В качестве второго рубежа обороны — приложение подключается **не суперпользователем**, а ролью `groshik_app`, у которой нет прав на DDL/DROP/TRUNCATE и доступа к другим схемам (см. `0011_roles_and_grants.sql`) — даже если инъекция где-то проскочит, она физически не сможет менять схему или дампить данные через права, которых у роли нет.

**MITM.** Локально (`docker-compose`) TLS выключен намеренно — трафик не покидает loopback-интерфейс; используйте явный `sslmode=disable`. На проде/staging (реальная сеть до managed Postgres) обязателен `sslmode=verify-full` с CA-сертификатом провайдера — просто `require` проверяет только факт шифрования, но не то, что сертификат принадлежит настоящему серверу, и уязвим к подмене. `sslmode=prefer` не используется: `libpq` и Node.js-драйвер `pg` трактуют его по-разному.

**Секреты.** `.env` в `.gitignore`, в репозитории только `.env.example` с плейсхолдерами. Реальные пароли/`DATABASE_URL` прода хранить в секретах CI/хостинга (GitHub Actions secrets, Supabase/Railway/etc. env vars), не в репозитории.

**Данные детей.** Ни в одной таблице нет полей имени, возраста, даты рождения, email, телефона или геолокации ребёнка или родителя. Единственное потенциально «текстовое» поле — `pets.pet_name` (свободный ввод), с `pet_name_status`/`pet_name_flag_reason` под простую модерацию нецензурщины на уровне приложения.
